# ERP Process Documentation Sample

A small set of business-analysis documents for a **made-up** company, "Sample Trading Co.", that is moving its order handling from spreadsheets into an ERP system. I wrote it to practice the paperwork a junior business analyst does: process flows, a user manual, a data migration checklist, and a requirements mapping table.

Everything here is fictional. No real company, customer, or system is described.

## The scenario

Sample Trading Co. sells office supplies to small businesses. Today, sales staff take orders by phone and email, record them in a shared spreadsheet, and the warehouse and accounting teams work from copies of that sheet. Orders get lost, stock counts drift, and invoices go out late. The company wants one system where an order is entered once and flows to the warehouse and accounting.

## What is in this folder

| File | What it shows |
| --- | --- |
| `01-order-to-cash-process-flow.md` | The "to-be" order-to-cash process as a flowchart, with a short description of each step and who owns it |
| `02-user-manual-create-sales-order.md` | A step-by-step manual for a sales clerk to create a sales order, with a "when something goes wrong" section |
| `03-data-migration-checklist.md` | A checklist for moving customers, items, and open orders from spreadsheets into the new system |
| `04-requirements-mapping.md` | A table that connects each business need to a system feature, a test, and an owner |
| `customers_template.csv` | A sample import file for customer records, with made-up data |

## How to read it

Start with the process flow (01) to see the big picture. The manual (02) zooms in on one step. The checklist (03) covers getting data ready, and the mapping table (04) ties everything back to the business needs.

## What I practiced

- Writing a process so each step has one owner and one clear output.
- Writing instructions in plain language that a new employee can follow.
- Listing what must be true before data is moved (clean duplicates, agree on required fields, test with a small batch).
- Tracing each requirement to a feature and a test so nothing is forgotten.
